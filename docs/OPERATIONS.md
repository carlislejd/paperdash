# Running Paperdash

Paperdash is a public-source analytics beta. It reads the official Papertrade HTTP endpoints and public trade stream, with Hyperliquid reference quotes for the asset price charts. It does not submit orders, connect a user's signing wallet, run a blockchain node, or currently decode canonical HyperEVM contract events.

Global trade observations, minute TVL samples, wallet cashflows/trades, raw history pages and portfolio batches are retained in our database. Protocol totals and current account details remain upstream snapshots with source timestamps. Wallet history has separate indexing and coverage status. A connected stream or completed source backfill is not proof of complete execution history. The upstream recent-trades feed is bounded, and its public stream does not provide canonical transaction identities. Do not describe this deployment as an independently reconciled ledger or a complete lifetime trade archive. The earlier [research plan](../research/DASHBOARD_PLAN.md) describes later canonical ingestion work; this document describes the implemented beta.

## Local development

Use Node 24 and the committed npm lockfile:

```sh
cp .env.example .env
npm ci
npm run dev
```

Vite serves the frontend at `http://127.0.0.1:5173` and proxies `/api` to the API on port 8787. With `DATABASE_URL` absent, the API runs its collector and a durable SQLite store. The example environment uses `.data/paperdash.sqlite`. Keep the database, `-wal` and `-shm` files together while running; stop the process before making a simple filesystem copy. Local collection fails visibly at `LOCAL_MAX_BYTES` rather than silently removing financial observations. Do not use local SQLite for multiple Render instances: their filesystems are ephemeral and not shared.

For local Postgres, set both `DATABASE_URL` and `REDIS_URL`, run `npm run db:migrate`, then run `npm run dev` and `npm run dev:ingest` in separate terminals. The API defaults to no embedded collector when Postgres is configured. Redis is required with Postgres so API replicas and the worker share one upstream request budget. Single-process SQLite development can use the in-process coordinator. Do not enable an embedded collector while intentionally running another collector against the same local store.

Production builds use `npm run build`; API and worker commands are `npm run start:api` and `npm run start:ingest`. `npm run db:migrate` is idempotent and serializes database migrations. Secrets belong in environment variables or the hosting dashboard. All `VITE_*` variables are public browser build inputs.

## Runtime database roles

The initial Blueprint injects the managed database owner's connection into both services. This makes schema bootstrap runnable, but grants more permission than a public API should retain. **It is not a least-privilege production setup.** The API writes current account/directory caches and prioritizes wallet indexing, so a strictly read-only role would break those operations.

Before broad launch, create separate API and ingestion login roles from an owner session on the private network, using the [credential handoff procedure](RUNTIME_ROLES_HANDOFF.md). It rejects missing or elevated roles, role memberships, runtime ownership and inherited schema CREATE. It leaves shared PUBLIC rights and unrelated objects untouched. The API receives retained reads, three cache/scheduling INSERT permissions and column-scoped UPDATE; the collector receives the exact projection/checkpoint permissions. Neither can update or delete immutable raw trade observations, history pages or portfolio batches.

## Retained history and indexing

The worker repeatedly sweeps the mutable wallet directory and discovers active wallets through trade observations. A wallet lookup enrolls and temporarily promotes that address. Three durable jobs per wallet cover cashflows, trades and portfolio history. The indexer reserves turns in the repeating order viewed ledger head, unfinished backfill, active portfolio, retry, active ledger head, unfinished backfill, active, oldest due. Profile lookups use priority 30, observed trades use 20, and top PAPER holder discovery uses 10. The viewed-head turn selects due cashflow/trade heads and independent head corrections for active priority-30 wallets; it borrows ordinary active-head, active, then oldest-due work when empty. The active-portfolio turn serves only due, unlocked portfolios for active wallets, including the top 100 positive PAPER holders enrolled by the existing directory rotation. It borrows active then oldest-due work when empty. This retains the existing two backfill turns, retry turn, fair turn and ledger-head reservations. Within each lane jobs remain oldest-due first; retry deadlines, leases and in-flight ledger exclusions still apply. The existing activation semantics retain the strongest priority while later activity renews its window; it expires ten minutes after the last activation, not necessarily the last profile visit. These are service preferences within the unchanged source budget, not promised freshness deadlines.

The retry lane selects failed primary or correction jobs only after their saved retry deadline and lease allow another attempt. It prevents a temporary timeout or source error from waiting behind an entire routine-refresh backlog. It uses the same request budget and backoff as every other lane; it neither raises concurrency nor bypasses `Retry-After`. Successful commits clear the error and remove the job from retry eligibility. Partial due indexes cover failed jobs so claiming a retry does not repeatedly scan every wallet's status JSON. A nonzero `failed` count describes jobs whose most recent attempt failed, not discarded records or permanently abandoned work; inspect their errors, attempt counts and last-success times before deciding on recovery.

Each default tick claims at most two jobs sequentially, then runs them together only when their wallet/history-kind pairs differ. Primary history and correction jobs for the same ledger never run together. Lower source concurrency reduces this width. Every started job settles before the next batch, shutdown or an unexpected persistence error can release collector ownership. The existing one-second pause after each default tick remains. Source 429 responses pause further claims until their retry deadline. The shared Redis budget still limits all HTTP request starts (including retries) and in-flight requests across API replicas and ingestion; the production defaults remain 250 ms between starts and three in flight. Bounded history batches leave capacity for global and foreground reads, but Redis admission is not a strict priority queue. WebSocket messages do not consume this HTTP budget.

Cashflow/trade pages commit normalized records, the original source page and a fenced checkpoint in one database transaction. A 120-second job lease expires if the process dies; its successor can resume from the saved cursor. Replaying a committed page does not blindly append another copy. Source-field/occurrence identities remain provisional, especially for cashflows with no unique source event ID. Changed source pages remain as raw variants even when a projection is updated. `backfillComplete` means the available source pages reached their end, not that we proved lifetime or canonical completeness.

New activity is refreshed from the head while deep backfill continues. A dedicated retry revisits observed pending cashflows for later status changes. If a main backfill cursor expires with a 400/404, indexing restarts that bounded scan from the head while keeping retained records. An invalid pending-correction cursor remains an explicit error with backoff; it must not silently become an unrelated head scan. Repeated cursors and malformed ordering are errors. Inspect them before resetting any checkpoint, and never delete retained records to force a retry.

Portfolio history begins with an available full-range fetch, then refreshes supported recent windows. Window selection considers both the last successful check and the source's retained coverage end; the last change sample is not a coverage boundary. Missing intervals are saved in `localGaps`, capped at 32 intervals by conservatively merging the oldest adjacent intervals on overflow. `localGapAfterMs` mirrors their earliest boundary for compatibility. Only a source-available window that spans an interval clears it; an incomplete full-range response is not automatically a repair. A successful expanded `1w`/`all` repair records `repairFetchedAt`, limiting coverage-driven expansion to once per wallet per 24 hours. Initial indexing, a new source generation and the existing weekly full reconciliation still obtain their baseline. Source-declared incomplete coverage alone never triggers repeated full downloads. Legacy unlocated gap flags stay conservative until reconciliation rather than forcing a broad-fetch surge.

Portfolio merges use the intersection of requested and source-available bounds. Incomplete windows preserve previously retained points outside the source's available interval; missing bounds permit upserts without deleting unseen points. Explicit source windows are half-open, preserving a sample exactly at their upper boundary. Quiet periods do not create local gaps, while known unrepaired joins remain disconnected in the chart. Each raw batch and its fenced checkpoint remain durable. A newer source generation can replace the active chart projection without deleting earlier raw batches, and older/invalid revisions are rejected. The API limits a portfolio response to 10,000 timestamp groups and preserves incomplete/gap coverage instead of claiming the truncated chart is complete. Source money values remain integer decimal strings; plotted values are display projections.

Wallet history endpoints use local keyset cursors, not expiring upstream cursors. Current account snapshots and directory results can still refresh through the shared source cache. There is no per-visitor upstream wallet-history download. TVL history is reconciled hourly by default and extended with continuously recorded minute samples. Global public trade observations are kept separately from wallet trade history; they are not merged into a falsely exact global execution ledger.

The hourly protocol-history refresh requests the source's `1h` interval so one coherent response can reconcile the seven-day chart window after source generation changes. The previous `1m` response covered only 24 hours and could leave an older day permanently split between generations. Existing minute TVL samples stay retained and live summary capture continues. Request spacing, concurrency, retry policy and refresh cadence are unchanged. History metadata records its interval: revisions are compared only within the same interval and generation, while the source-time regression guard applies across intervals. Daily bars still require valid midnight boundaries and a coherent generation; missing data is never filled with a residual from lifetime totals. Charts show seven UTC days, so their visible sum is not a lifetime total once older days leave the window.

Additive chart cards show the latest bucket separately from the selected-period total. Wallet cards label the account's lifetime realized trading P&L and exclude staking rewards. These labels do not alter stored amounts or fetch additional wallet data.

Opening a wallet gives its existing shared account refresh up to 1.5 seconds to complete before returning saved or unavailable account data alongside retained history. Slow work continues under the same shared admission and cache lock; this response budget does not create a second source request. The drawer makes at most two early follow-up reads while that refresh is pending, then uses its normal visible-only 15-second cadence. The account cache TTL remains 30 seconds. `accountFreshness` describes the account check and source timestamps independently of history; a successful history backfill does not keep an unopened wallet's current balance snapshot warm. The PAPER ownership tile sums staked and unstaked raw amounts and shows the separate balances.

An inactive account's `indexedThroughTimestamp` can remain at its last indexed change even after a fresh successful stream bootstrap. Freshness therefore requires a valid, nonregressing account snapshot with a recent successful receipt and no account error, rather than requiring activity every 30 seconds. Future/invalid clocks and stale receipts still fail closed; price clocks remain independent for margin scenarios. The UI labels the two clocks as last account update and checked time. P&L cards show account/history check times and an Update card action that recaptures already-loaded data while preserving layout and privacy; it does not force another API request.

Full account stream bootstraps can reset `accountRevision` even as indexed chain progress advances. Both the API cache and wallet drawer reject a full snapshot only when its indexed block or indexed timestamp regresses; an equal or newer pair of indexed clocks remains eligible after a revision reset. The revision still identifies a snapshot for matching risk data, but is not a globally monotonic age marker. A retained snapshot keeps its own account freshness and risk metadata.

From a worker shell with its existing environment, run `npm run ingest:status` for heartbeat, stream lifecycle diagnostics, queue counts and the oldest due job. Add `--` followed by a full wallet address for that wallet's checkpoints. The command exits nonzero if the saved collector heartbeat is older than 30 seconds. `/api/indexing` reads the worker's periodically saved aggregate and reports its timestamp; it does not perform a full queue scan for every caller. It marks a missing or more than 90-second-old queue snapshot stale even when another collector loop keeps the heartbeat fresh, and also marks status-publication failures stale. A healthy heartbeat alone does not establish that every history job is progressing: watch pending/failed counts, oldest due time, per-wallet last success and retained counts together. Full backfill time depends on source limits, wallet count and history depth.

The additive `activeDue`, `backfillDue`, `maintenanceDue` and `correctionsDue` counts partition `pending`, including due work currently leased. Active work includes corrections for temporarily active wallets. Among inactive work, `backfillDue` covers primary jobs with incomplete initial history or a non-null continuation cursor; `maintenanceDue` covers completed primary jobs waiting for their next check; `correctionsDue` covers independent corrections. `oldestActiveDueAt` and `oldestBackfillDueAt` separate priority freshness from aggregate catch-up age. These categories describe saved due work, not counts of missing transactions. Observe several snapshots rather than inferring throughput from one changing total; new wallets and recurring jobs continually enter the queue.

The hosted collector continues when a developer's laptop sleeps or loses power. Do not reset checkpoints because a local session ended. Confirm the cloud heartbeat and advancing completed-job counts first. Cold wallet cashflow/trade heads start with a six-hour refresh target. A complete, unchanged head cycle raises the next interval to 12 hours, then a second unchanged cycle to at most 24 hours. New records, corrected payloads or activity reset that quiet-cycle streak. The streak and changes seen across multiple pages survive restarts. Initial backfills and pending-withdrawal correction cadence are not slowed by this policy; cold portfolios retain their daily refresh and periodic full reconciliation. No overdue job is moved into the future simply to reduce backlog counts: a successful fetch and fenced commit must precede its new schedule.

Opening an affected wallet or observing a trade advances eligible jobs to the active cadence without deleting records or bypassing retry deadlines. Activation during an in-flight cold request is serialized with its checkpoint so it cannot leave an active wallet scheduled 24 hours away. Active ledger and portfolio targets remain one and five minutes respectively, subject to backlog and the shared source limit; current snapshots and TVL can lead retained history. `backfillComplete` in the indexing aggregate counts completed history jobs, not wallets.

A rollback preserves retained samples; rolling back the worker stops new quote capture and the new chart should become delayed.

## Position holding time and leverage

`GET /api/position-metrics` and `GET /api/wallets/:address/position-metrics` serve saved sums and counts over retained closed/liquidated positions. Both means use the same valid, unambiguous cohort and weight each position equally; the global mean divides total sums by total positions, never by the number of wallets. Empty means are `null`. The UI labels global coverage as partial indexed history and reports sample/excluded counts. These are all-retained-history metrics, separate from the rolling 24-hour leaderboard. Current open-position rows come from the wallet snapshot and stay separate from closed metrics. See [definitions and verified source fields](POSITION_METRICS.md).

Four additive tables retain a pending-record queue, per-record contributions, wallet/global rollups and a durable legacy cursor. Each trade-history commit marks changed retained records in the same fenced transaction as its checkpoint. The collector processes at most 500 legacy keys and 500 queued records every five seconds, retaining progress across restarts. Each projected correction subtracts the prior contribution before adding its replacement. Aggregate sums are stored as exact decimal integers; only displayed means use floating-point numbers. API reads use keyed rollups and bounded queue/status checks, with no history scan or additional upstream requests. Existing available history is projected once; no source backfill is reset.

The wallet-only `highlights` extension adds best/worst recorded adjusted PnL and a separate valid-outcome count to the existing cached metric response. Two compact projection tables retain normalized outcome facts and wallet counts. A binary/C-collated, fixed-width offset of signed int256 PnL lets two indexed `LIMIT 1` lookups find exact extrema across all retained outcomes, including values differing by one raw unit; neither endpoint scans raw history. The existing queue handles corrections, ambiguity and removals atomically with both projections. Legacy cursor `id=2` performs a second bounded local projection and resumes across restarts without resetting source checkpoints or the older means cursor; matching mean facts and unchanged replays are not rewritten. `tradeCount` excludes ambiguous/invalid outcomes, remains independent of holding-time validity, and is `null` until known rather than inventing zero. A checked-empty set can report zero. `highlights.complete` requires its own projection caught up, available wallet history scan complete and no excluded outcomes; this never promises universal lifetime capture. Existing coverage and stale flags still apply. Restricted roles need the new table grants before rollout. Source API limits, polling cadence and upstream request counts are unchanged.

`position_metrics_wallet_state` admits up to 1,000 unfinished known-wallet requests from the shared profile-metrics cache loader. It stores a durable local keyset cursor; repeated requests never reset progress or rewrite completed work. Each collector tick may serve up to eight requested wallets sharing at most 250 of its existing 500 scan turns and 250 of its existing 500 projection turns. Unused work returns to the global path, which retains at least half the budget. A wallet can finish before the global address-ordered cursor reaches it, but completion still requires its keyspace exhausted, its correction queue drained and available source history checked. New records and corrections reuse the existing atomic queue. This adds a small table/index and narrowly scoped runtime grants, with no per-viewer history scan or upstream request. The compatible API migration must run before API/collector rollout; older collectors safely ignore local demand until upgraded.

Deploy the additive migration with the API, then the compatible collector, then the frontend. Restricted runtime roles require the grants above before deployment. Confirm both metric endpoints, advancing or completed projection status, empty `null` means when appropriate, and ordinary history indexing. Rollback to an older collector stops marking corrections for this projection; reconcile its missed record keys before treating rollups as current again. No Render resource or plan changes are needed.

## Freshness, incidents and recovery

Distinguish process health, database availability, collector heartbeat, stream connectivity and source age. Empty trades and stale upstream data are different states. A successful HTTP response must not turn an old snapshot into “live.” Watch collector errors and response status alongside the last stored timestamp. The public-source beta cannot recover every missed execution from the short recent-trades window; after a prolonged source outage, preserve the gap in coverage.

The internal `stream-diagnostics` snapshot retains the latest lifecycle event and sanitized reason/code with client/subscription states. `npm run ingest:status` exposes it in the worker shell; it is not a public endpoint. Terminal disconnects and unsubscribes must be visible even when HTTP polling remains healthy. The Centrifuge client already retries ordinary temporary transport failures. Do not install a blanket reconnect loop that overrides explicit authentication, protocol, connection-limit or forced-disconnect refusals; diagnose the recorded reason before further recovery attempts.

For an upstream failure, keep cached content readable with its timestamp, inspect throttling/network errors, and reduce request pressure when necessary. Never reset source timestamps or substitute demo data. For a Redis failure, verify database-backed reads and stream resynchronization, then restore Redis; Redis is not the source of durable history. For a Postgres failure, inspect Render's HA event, allow clients to reconnect, and verify the worker reacquires its collector lock. HA asynchronously replicates and can lose the most recent writes during failover. It does not create complete upstream replay where none exists. [Render HA limitations](https://render.com/docs/postgresql-high-availability).

Before launch, prove the following with the deployed topology: collector restart, overlapping worker deploy, API instance restart while a browser is streaming, replay after a browser reconnect, slow-client disconnection, Redis interruption, database failover and backup restoration. A configured topology is not evidence these production paths have passed. Keep the source-backed coverage status visible throughout recovery.

Paid Postgres on Pro provides seven days of point-in-time recovery. Restore to a **new** database, verify stored observations, wallet records, raw pages/batches and indexing checkpoints, then switch both API and worker connections together. Stop the old worker before activating the new database's worker so only one database accepts new observations. Allow restored job leases to expire before expecting those jobs to resume. Preserve the old database until validation is complete; deletion also removes its associated recovery material. Do not use production as a restore target. [Render backups](https://render.com/docs/postgresql-backups).

A separate PITR copy `dpg-db56a3h42hec73fsbcu0-a` restored the 16:08:20 UTC state with external access blocked. Read-only private SQL matched production's immutable records at that cutoff: 28,692 trade observations, 21,640 raw pages and 11,214 portfolio batches. It also verified 10,521 wallets, 31,563 job checkpoints, 22,223 retained history rows, 18,476 chart points and a heartbeat 129 ms before the target. Available status took about two minutes; validation completed within about four minutes. No production cutover or checkpoint reset occurred. See [drill details and limitations](LAUNCH_CAPACITY.md#recovery-and-backup-readiness). The temporary copy was deleted after validation; the original five production services and the production export remain. Estimated prorated drill cost was below $0.02, pending the actual invoice.

PITR and the HA standby are not independent long-term backups. Before public launch, configure encrypted logical exports in an external bucket with restricted credentials and retention, then test a restore. ## Rollback

Keep each production commit and its environment changes recorded. Roll back API/worker/frontend code to a known compatible commit; the UI build embeds the API URL, so a frontend rollback also restores its old URL configuration. Use additive schema changes and keep at least one release of compatibility. A code rollback does not reverse a database migration, restore overwritten snapshots, or recreate missed upstream history. If data was corrupted, restore a separate database and reconcile coverage before switching traffic.

Do not attach persistent disks to the API or worker as a shortcut: replicas cannot share them and Render disk-backed services cannot scale horizontally. The database remains the durable shared store. [Persistent disk constraints](https://render.com/docs/disks).

## Shared panel notifications and wallet check ages

The collector publishes a bounded `panel-revisions` manifest for House, protocol charts, PAPER economics and liquidation statistics through the existing event log and EventSource. A saved panel must commit before its revision is advertised. Manifest writes serialize, coalesce for one second, and renew a ten-second capability heartbeat. The heartbeat does not replace a panel's actual source or publication clock. Bootstrap includes the optional versioned manifest in the existing overview frame, preserving stream IDs and old-client compatibility. There are no new upstream requests, quotas, tables or deployment settings.

The browser shares one request controller per exact mounted URL. Supported panels invalidate on changed revisions with a five-second request floor and jitter; unchanged panels reconcile every thirty seconds. Each saved body includes an additive `panelRevision` matching its publication hint. A successful HTTP response alone does not acknowledge a revision: an older edge-cache response gets one bounded follow-up, then slow reconciliation if it still cannot be confirmed. A missing, invalid or expired capability, an old server, or a disconnected stream restores ordinary polling. Unsupported endpoints keep their existing cadence. Retry-After/backoff remains in force across hints and remounts. Hidden pages pause reads; last good values survive request failures and are labeled delayed as their clocks age. Unchanged heartbeats retain React snapshot identity to avoid extra chart renders. This reduces redundant snapshot reads, not the upstream source's inherent latency; rapidly changing panels may still refresh at approximately their prior cadence.

`/api/indexing` includes `activeFreshness` in the existing collector-saved status sample. `asOf` is the sample time. `byKind` groups primary cashflow, trade and portfolio jobs for currently active wallets into disjoint successful-check age buckets: less than one minute, one to five, five to fifteen, fifteen to sixty, and at least sixty minutes. Missing, invalid and future check clocks are counted separately. `oldestSuccessAt` excludes missing/invalid/future clocks. The collector calculates at most three grouped rows on its existing thirty-second status interval; API viewers read the saved snapshot. An empty group means no currently active wallets in that sample, not zero latency.

These ages measure last successful primary-job checks, not source event age, completion of an entire multi-page cycle, coverage completeness, or time spent waiting since activation. `oldestActiveDueAt` may inherit a cold wallet's old due timestamp when it becomes active, so it must not be reported as activation-to-refresh latency. Correction jobs retain their separate queue counts and do not enter these primary-check buckets. Check the status sample's own age before interpreting any bucket.

Roll out API, collector, then frontend from the same tested commit. The optional envelope permits mixed versions; fallback polling remains available throughout. Verify a valid manifest on stream bootstrap, changing revisions after committed publications, original source clocks, and stale/fallback behavior. Keep the current source limits and Render topology unchanged. This focused rollout is not a new production surge/load-capacity validation.

## Asset delivery, collector writes and loading stability

Asset pages reuse the existing selected-asset stream to reduce snapshot downloads. A valid, fresh price publication on the current `asset:N` subscription enables all-trader market and open-interest/activity reconciliation every 15–18 seconds, shortened when their original receipt or source clocks approach the freshness boundary. Profitable views retain ordinary five-second polling with jitter because classification arrives through saved snapshots. These REST-only values never borrow the live price clock. Stale snapshots (including the retained historical intake-gap flag), disconnected streams, changed topics, or a selected asset silent for 20 seconds restore ordinary polling. Manual refresh, Retry-After, error backoff and hidden-page suspension remain in effect; REST continues to supply authoritative history corrections and coverage.

Opening a wallet adopts an in-flight hover request or reuses its response for the remainder of the original 15-second local cache interval. A cache hit does not renew any source or receipt timestamp. Pending account refreshes retain two bounded two-second rechecks, and explicit retries bypass cached-response reuse. Unclaimed hover work remains cancellable and timed out.

The collector coalesces overlapping overview publications. Only changes to summary/history/account count or committed trade intake require rereading overview inputs; unrelated loops reuse those inputs and recompute health. Unchanged overview bodies are not rewritten. Heartbeats persist at most every five seconds while health is unchanged, with immediate writes on health transitions. Snapshot replay cursors are captured before full source reads; health-only updates retain their original cursor, and identical full reads may advance the saved cursor at a bounded ten-second cadence. A lost trade commit acknowledgement triggers source reconciliation before retrying, so a successful but unacknowledged write cannot disappear from the saved overview.

Each portfolio job checkpoints the last applied projection digest atomically with its records. An unchanged projection skips point deletion/reinsertion but still records successful checks and retains new raw source revisions. Digests include replacement bounds, inclusive/half-open end semantics, source generation, ordered duplicate-time samples and gaps. An intervening correction or window change invalidates the optimization. The optional checkpoint field needs no schema migration; an older worker safely ignores it, and a job without it performs the normal reconciliation.

Loading layouts reserve the PnL image's actual aspect ratio and keep wallet/leaderboard column widths consistent with their placeholders, including hidden mobile columns. Short-page footers stay anchored as small result sets grow. These changes preserve scrolling and existing export/accessibility behavior.

Local regression fixtures measure request counts, overview reads/writes, portfolio mutation statements and desktop/mobile geometry. These are deterministic implementation checks, not production speedup or capacity claims. After rollout, compare request counts, stale-label behavior, database writes and field layout-shift metrics against the October 14 baseline before changing hosting capacity.

## Independent chain reads and relayer tools

The PAPER collector is enabled by default. `HYPEREVM_PAPER_ENABLED=false` returns newly published PAPER responses to their API sources without deleting chain evidence or reward baselines. `HYPEREVM_RPC_URL` defaults to the public Hyperliquid endpoint; keep private-provider credentials server-side. `HYPEREVM_PAPER_INTERVAL_MS` defaults to 30,000 and accepts 30,000–60,000. Each run normally makes ten bounded RPC calls, with a 20-second overall deadline, 64 KiB response limits and HTTP Retry-After handling. A latest call can expose its execution-context block number before that exact canonical header is queryable. Only the observed `-32603` error naming the requested height permits up to two header retries, one second apart, under the same overall deadline. The financial call is never replayed; unrelated errors and header mismatches fail closed. Only the leased collector runs it; visitors and API replicas make no RPC calls. The default cadence consumes at most twenty-four requests/minute including both header retries, leaving headroom under the public RPC's documented 100/minute/IP limit. Separate tools sharing the same IP consume that same allowance.

The financial reads use one `eth_call` to a Multicall3 deployment whose runtime matches its published deployment transaction. Supply, `totalStaked()`, staking token custody, the reward accumulator, decimals, chain ID and execution clock come from that call. PAPER/staking implementations and runtime fingerprints are checked before and after as applicable; an upgrade or custody mismatch stops new observations. The total-staked getter is supported by selector/custody comparison against this pinned deployment, not a claim of a complete verified staking ABI. Raw values remain decimal strings.

The public RPC's call clock was one second behind its matching canonical block header in live checks. Both timestamps are retained; reward intervals and `onchain.sourceAt` use the actual call clock. Number, parent hash and header are checked, and more than two seconds of timestamp difference fails closed. This bound is a measured provider-compatibility rule, not a protocol timing guarantee. The saved block hash comes from the subsequently fetched header; this does not cryptographically pin the preceding latest-state simulation to that exact fork. All financial values are atomic within their simulation, not a proof of finality. Historical state calls are never used to invent a baseline. [Live reader evidence](evidence/2026-10-23-hyperevm-read.json).

The existing snapshot store holds `onchain-paper` and a separate `hyperevm:` reward-history namespace, so no database migration is required. The public economics response includes onchain provenance/freshness. Chain fields expire after 90 seconds, collector-health failure, or a recorded RPC failure; protocol allocation/history clocks remain separate. Repeated chain heads never renew receipt time. Failed reads retain the last complete publication. The new annualized reward window needs one measured hour. Older API daily rows remain available before the chain cutover; overlapping or incomplete boundary intervals are not stitched together.

For raw event evidence, run `npm run chain:archive -- --help`. Supply an explicit SQLite path, deployment identity, contract addresses and start block; repeat the same scope to resume. Each run and each log range are bounded. Checkpoint, blocks and logs commit atomically; ancestry conflicts, malformed logs or storage limits stop collection without deleting evidence. The defaults cap storage at 128 MiB, 100,000 logs and 100,000 blocks. This archive is operator-invoked and is not scheduled or connected to production analytics. It cannot certify that an RPC omitted no logs. Verified event ABIs and historical deployment boundaries remain necessary for a complete trade index.

`npm run relayer -- verify` checks the current official frontend against pinned source fingerprints. `queue ADDRESS` reads relayer queue positions, and `prepare PATH.json` produces unsigned EIP-712 data with explicit decimal-string amounts, nonce and Unix-second deadline. The CLI accepts no signing keys and has no submit command. Source changes fail verification until reviewed. [Captured interface evidence](../research/sources/relayer-2026-10-22.json).

The library's `submitSignedRelayerIntent` requires an already signed payload and an expected intent ID, re-verifies the interface, and sends exactly once. It distinguishes known rejection from an uncertain outcome; an acknowledgement or reported confirmed state is not an independently verified execution receipt. Caller-owned nonce persistence, signer recovery, authorization, balance/market checks and outcome reconciliation remain prerequisites for a trading UI. The dashboard has no signing or submission route. Submission tests use mocked transports; no live execution was performed.
