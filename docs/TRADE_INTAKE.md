# Trade observation continuity

The collector normalizes each received trade once, then keeps the same observation ID through admission, projection, and retries. A stream observation without a verified source execution ID receives one UUID at receipt; retrying it does not create another UUID. Recent-API observations retain their source-derived ID. Equal economic fields do not collapse distinct stream observations.

Admission has two stages. Memory holds at most 1,000 normalized rows and 1 MiB, including the batch currently being saved. The PostgreSQL or SQLite inbox retains admitted rows across collector restarts. Each database append accepts at most 50 rows atomically, ignores existing IDs, and avoids re-admitting observations already in the durable trade ledger. The inbox is capped at 100,000 pending rows and 128 MiB of encoded payload. A singleton accounting row changes in the same transaction as append/acknowledgement; PostgreSQL row locking prevents concurrent admissions from exceeding either cap.

One runner persists memory batches and reads at most 50 inbox rows at a time, projecting at most ten per turn. It calls the existing atomic trade writer, always schedules wallet history discovery even when that writer reports an existing trade, then acknowledges the inbox row. Projection, discovery, or acknowledgement failures retain the head for retry. Backoff increases from one second to a maximum of 15 seconds. A committed write whose response was lost is retried with the same ID, so its trade, rollup contribution, and replay event are not added twice. Missing wake-up notifications are recovered by the API's periodic database event tail, subject to the normal finite replay retention.

Malformed rows do not discard valid neighbors. A persistent gap marker records the earliest known incident and the latest incident's kind, time, and known rejected-row count. That count describes the latest incident, not total missing source activity. Capacity pressure pauses admission and unsubscribes from the public trade channel without deleting retained work. After memory falls below half its limits and durable backlog is below 10,000 rows and half its byte limit, admission resubscribes. Recovery never clears the historical gap marker. An old pending head also marks activity delayed while the inbox catches up. Heartbeat diagnostics expose memory depth, durable depth/bytes, oldest receipt, retries, admission pause, and gap evidence.

On shutdown, admission stops immediately. The collector flushes memory to the inbox; it only projects during shutdown if that is needed to make durable capacity for memory. Already-durable backlog can be left for the replacement. A total 40-second intake deadline rejects shutdown so the worker exits without releasing its lease while a write might still run. The independent PostgreSQL lease-loss fail-stop remains active. If PostgreSQL is unavailable, an unconfirmed memory remainder can only be reported best-effort in the process log; its shutdown gap marker is not promised durable.

This guarantees replay of rows whose inbox transaction committed. It cannot guarantee capture before that commit, during a database outage followed by process loss, during source disconnection/overflow, or for events the provider never publishes. The public stream has no verified replay/acknowledgement contract. The recent endpoint reconciles only its newest 50 rows. This remains explicitly partial public-source observation data, not a canonical chain index.

The additive schema requires `trade_inbox`, `trade_inbox_totals`, and `trade_ingestion_gaps` (prefixed `paperdash_` in PostgreSQL). Apply the owner migration and the tested runtime-grants SQL before starting a new collector. The API checks schema existence through the catalog and receives no raw-inbox privileges. Pending inbox rows and gap evidence have no automatic expiry.

Focused tests cover successful commits followed by simulated lost replies, unchanged retry IDs, wallet-priority recovery, valid batch suffixes, restart replay, malformed neighbors, memory overload/recovery, byte and row caps, concurrent PostgreSQL admission, repeated acknowledgement, and shutdown with a full inbox or unresolved database operation.
